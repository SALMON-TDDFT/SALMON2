# W q-loop OpenMP implementation plan

Approved by the user's “進めて” after the MPI-k / OMP-q design.

Goal: share the target-k rotation across q workers, keep MPI outside OpenMP,
use thread-private reusable scratch and single-thread BLAS.

Architecture: optional Fortran C-interoperable shared library called by Python;
bounded batches of q sources/phases; one parallel region around each batch's
q loop. Existing scalar reference remains default. Packing/snapshot I/O remains
in Python. Moving all input management to native code is out of scope.

1. Add numerical tests against existing resolvent_gram/broadened_gram, including
complex rotations, fractional occupations, eta/2, varying G counts, nonfinite
rejection and one/four threads. Observe missing implementation failure.
2. Implement audited native module and ctypes bridge; make optional q-thread
backend available in equilibrium/pump solvers and prepare_w CLI.
3. Audit source and all native objects before linking/use; immutable fresh build
and SHA record. No SALMON executable or production job changes.
4. Run kernel, full-W, MPI and numeric error tests. Measure fresh interleaved
8x1 / 4x2 / 2x4 with same backend plus original Python reference. Record actual
OMP team size and full-W time; do not claim gain without measured improvement.
5. Document build/launch, memory bounds, library threading, and limitations.
Store collected records in canonical calc2026, no GS data collection.

User steering: Fugaku must use at least 12 OpenMP threads per MPI rank.
Native numerical tests include 12 threads; Mac 1/2/4 tests are local diagnostics
only. Future Fugaku performance runs start with 12 threads and vary MPI ranks.
No remote production launch or replacement is authorized by this note.
