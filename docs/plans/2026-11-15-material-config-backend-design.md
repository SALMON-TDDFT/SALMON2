# 物質ID・共通設定・交換可能バックエンド設計（改訂版）

状態: 実装前の設計。会話中の入力例・登録APIは、以下の契約へ整理する。ここで提案するAPIやJSON形式を、現在利用可能な機能として案内しない。

既存のGS/TDDFT共有状態分離の作業リストを維持し、設定を切り出す段階でこの設計へ接続する。新しいXC検証を先行させない。本設計はGS内部構造の独立化が完了したことを意味しない。

## 1. 目的と採用する構成

利用者は物質IDを付け、物質ごとに物理・数値パラメータを指定する。そのIDは初期状態の準備、配置、MPI割当、応答、出力、再開まで保存する。SALMON組み込み実装に加え、利用者のPython、C/C++、Fortran、外部プロセスを同じ配置・実行計画に組み込めるようにする。

採用する構成は「共通設定層＋明示登録されたバックエンド」。共通層へ全物理モデルのパラメータを列挙する方式は、拡張のたびに本体改修が必要になるため採用しない。一方、任意JSONを検証せず渡す方式も採用しない。

共通層はID、参照、単位表現、資源、設定の寿命を扱う。モデル固有のパラメータと条件は担当バックエンドが検証する。数値カーネルは物質IDやSALMON内部型を知る必要がない。

## 2. 分離する対象

| 対象 | 内容 | 所有・変更 |
|---|---|---|
| 物質定義 | model、backend参照、物質固有パラメータ | 利用者が指定。実行計画確定後は不変 |
| 初期状態 | 特定の物質の初期データ、準備条件、形式・内容識別 | 不変。複数点から参照可能 |
| 配置 | 形状・層厚・材料参照とマクロ点への割当 | 計画時に展開・保存 |
| 時間発展状態 | 各点の波動関数、密度行列、分極、履歴など | 点ごとに独立、バックエンドが所有 |
| 場 | 電磁場格子・境界・光源と場の状態 | 物質の電子格子と別に保持 |
| 実行計画 | ホストMPI群、点の担当、群内分割、スレッド数 | 物理設定と別。明示的に検証 |
| 実行記録 | 採用設定、ID対応、版、ハッシュ、結果 | run単位で保存 |

同じ物質定義を複数の実行群へ割り当てられる。ランク割当をmaterial_idの辞書へ直接埋め込まない。

## 3. IDの契約

- `material_id`: 利用者が付ける物質定義のID。モデル・パラメータを参照する。
- `initial_state_id`: 具体的な初期状態のID。`material_id`へ参照を持つ。同じ物質に複数の初期状態を許す。
- `point_id`: 展開済み配置の点ID。MPIランク番号や配列順とは独立。
- `run_id`: 実行のID。通常は自動生成する。
- `group_id`: 実行群のID。物質IDとは別で、複数点の担当を表せる。

通常の一状態/点では`run_id + point_id`を状態の論理識別に使う。分岐や点内の複数サブモデルが必要な拡張では、branch/state/component IDを追加し、親の対応を残す。現段階で一つの点へ複数の主物質状態を黙って割り当てない。

IDは大文字小文字を区別する不透明な文字列とする。空文字、前後空白、制御文字、重複JSONキーは拒否する。Unicodeを黙って正規化せず、入力どおり保持する。表示名は別のlabelで指定できる。IDをそのままファイルパスに使わない。

内部の整数番号が必要なら双方向対応表を生成する。順序変更・MPI再分割でIDを変更しない。層などから生成したpoint_idは展開済み配置に保存し、再開時に再生成しない。幾何形状の変更は新しい配置として扱う。

界面処理はIDの大小・連番・名前から物性を推測しない。接続関係、媒質特性、明示した境界条件で決める。同じ物性を異なるIDで定義しても人工的な界面応答を発生させない。

## 4. backendとmodel

`model`は物理モデルの名称、`backend`はその計算を担当する登録実装への参照。組み込みモデル名だけの閉じた列挙にはしない。自作モデルは名前空間付きの名称も登録できる。

バックエンド記述子は次を持つ。

- ID、実装版、契約版、モデル名、役割（物質応答／場／初期状態準備など）。
- パラメータスキーマの版・ダイジェストと検証関数。
- 単位・符号・時刻配置、対応する駆動ポート。
- 対応する実行方式と並列分割制約。
- 状態保存、複製、追加観測量などの能力。
- 実装・外部データの由来情報。取得できない情報はunknownと明記する。

`parameters`の中身はバックエンドが解釈する。共通層は、その内容を展開済み設定へ保存できることを要求する。スキーマを持たない自作モデルもPythonから登録できるが、validate/resolve相当の明示的検証と保存可能な採用設定は必要。スキーマ未提供ならAIによる設定自動作成は提供しない。検証なしの通過は認めない。

JSONからPython式・任意import先・シェルコマンドを実行しない。Pythonホストがregistryへ明示登録する。外部ライブラリのロード・ワーカー起動も登録アダプターが担当し、設定検索やimportの副作用として行わない。

## 5. 共通設定モジュール

提案する`salmonpy.config`の責務は次のとおり。

1. schema版確認、重複キー・未知キー・型・有限性の検査。
2. 明示単位の正規化、既定値展開、指定値/補完値/由来の記録。
3. ID参照と初期状態との整合検査。
4. バックエンド固有の値・組合せ検証への委譲。
5. 配置展開、実行群への割当、能力・資源条件の照合。
6. 不変な解決済み設定、確認用要約、保存用manifestの生成。

JSONとPythonオブジェクトは同じ検証経路へ入れる。Python利用でJSONファイルを必須にしない。ファイル参照の相対パスは入力ファイル所在ディレクトリを基準に解決し、Pythonからは基準ディレクトリを明示できる。記録には移設可能な参照と内容ハッシュを使い、絶対パスを同一性に使わない。

単位を伴う入力はvalue/unitを基本とする。初心者向けの推奨既定を表示できるが、物質・電荷・XCなどの意味を変える条件を黙って推測しない。グリッド幅と点数の矛盾は拒否し、セルに合わせた丸めは採用値として明示する。電子グリッド/k点は各物質の設定、FDTD格子は場の設定とする。

共通既定値は省略補助に限定し、優先順位を「機能の既定→明示した共通既定→物質固有指定」と固定する。未知キーは停止。配列は要素単位の暗黙マージをせず置換とする。null、未指定、空配列を区別する。

JSON SchemaとAI検索項目は登録定義から生成する。複数項目間の意味的制約や実行時資源条件は、Schemaだけで保証せず検証関数を用いる。AI検索は案内であり、曖昧検索結果で実行キーを置き換えない。

## 6. 物質応答の契約

既存のPython契約を基準にする。

```python
initial.new_state(dt=..., time0=..., initial_A=...)
state.step(A_next)
state.current
state.time
state.timing
state.close()
```

結晶の応答はA駆動のみ。境界のAはSALMONのAc=A/c、電流は電荷電流密度j。単位、入力/出力の時刻配置、t=0の扱いを既存のtiming契約で宣言する。初期Aが非ゼロの利用可否も能力/入力条件として検査する。

必須なのは独立状態の生成、宣言に従う一ステップ、観測、明示解放。`close`のない軽量な既存モデルにはラッパーがno-opを提供できる。入力配列を変更しない、受け取った一時バッファを無断で保持しない、出力の形・有限性を守る。保存や観測のたびにバックエンド内部の可変配列を無断共有しない。

物質ID・点IDはホスト側のbindingが保持する。MPI集団コールバックには担当点の情報を渡せるが、最小の数値カーネルはAと自身の状態だけで動かせる。通信用配列はメッセージ全体の点順対応表とstep番号を伴い、位置だけからIDを推測しない。

LD単独の基本入力はEであり、結晶用A契約を強制しない。A端点からEを作る既存アダプターと、FDTDのE/H結合を明示的に使い分ける。時間差分や符号変換を黙って挿入しない。場のバックエンドも別の契約として登録可能にし、物質モデルへMaxwellソルバーの実装を要求しない。

## 7. 準備・実行の流れ

提案する登録アダプターの責務はdescribe、validate/resolve、prepare、new_stateへの接続。既存実装へ新しいメソッドを直接追加することを必須にしない。

```text
JSON/Python入力
  → registry照合・共通/固有検証
  → 物質/初期状態/配置/実行計画の確定
  → 短い条件要約・解決済み設定の保存
  → backendによる初期状態の準備
  → 点ごとに独立した状態を生成
  → 宣言した場–物質結合で時間発展
  → 出力保存・状態と資源の解放
```

初期状態は外部のGSアーカイブだけでなく、利用者データや平衡LD状態でもよい。prepareはin-memory表現も許す。再現用には生成レシピ、バックエンド版とデータ識別を残す。ゼロ初期値の暗黙代入は、バックエンドが物理的な既定として定義した場合に限る。

大量点ではimmutableデータの共有・まとめた更新を任意最適化として許す。ただし点ごとの可変状態の独立性を維持する。準備データのcloseは、そのデータを使う全状態の解放後に行う。

## 8. 能力宣言と失敗契約

能力は単なるbackend名から推測せず、選択した設定と実行方式に対する適否を検査する。

- 実行方式: serial-in-process、collective-MPI、external-process。
- 複数状態: independent-instance、single-instance-per-processなど。
- optional: checkpoint、restore、clone、batch、追加観測量、可変dt、スレッド同時実行。
- failure semantics: atomic（失敗後も同じ受理状態）、invalidates-state、process-fatal。

既定は固定dt・同時呼び出し不可。能力を宣言しただけでは検証済みとは扱わず、適合試験の範囲を記録する。

独立した物質stepの原子的失敗と、複数物質＋場の一ステップ全体の原子性は別である。結合途中で失敗した場合、全要素が復元能力を持ち、結合側で復元を実装・検証した場合だけ継続可能とする。それ以外はセッションを無効化して停止する。自作モデルに実装できないrollbackを見せかけで提供しない。

追加観測量は既定では後処理用の出力であり、温度などを別モデルへフィードバックする結合とは区別する。フィードバックには入力/出力ポート、単位、時刻配置、依存関係を明示した拡張契約が必要で、追加出力名だけから結合を推測しない。

能力が足りない場合は、要求した機能（例: checkpoint再開）を実行前に拒否する。保存不要の計算まで禁止しない。

## 9. MPIと実行資源

ホスト/ランチャーがMPIを開始し、利用者指定のworldから実行群を構成する。ライブラリがimport時にMPIを開始したり、新しいMPI_COMM_WORLDを作る設計にはしない。

バックエンドへ渡すgroup communicatorは借用であり、worldの置換ではない。バックエンドはその範囲で通信し、必要なら複製・分割して所有する。借用commを解放せず、MPI_Finalizeを呼ばない。群外/ホストworldへの集団通信を行わない。バックエンドが作ったcommは担当バックエンドが解放する。

collective-MPIではprepare/create/step/closeのうち集団呼出しが必要な操作、呼出しランク、Aの配信方式、jの返し方を宣言する。jが群内で複製済みか、局所寄与か、leaderだけが保持するかを区別し、二重加算しない。

直列モデルを複数ランクで呼んでも内部並列化にはならない。既存の直列モデル用MPIアダプターは1ランク群を基本とする。

- 重いTDDFT: まず一群一物質・一マクロ点。群内並列はバックエンドに委譲。
- LD主体: 各FDTDランクが担当領域内の多数のLD状態を保持。LDごとの専用群を作らない。
- 自作並列SBE等: 宣言した群内並列を使う。
- 外部プロセス: 登録アダプターが所有・監視。追加ランク/スレッドも資源予算に含める。

同一のスキーマが異なる物質設定を表現できても、現在の組み込みバックエンドが同一プロセスで扱えるとは限らない。制約を検査し、明示的な別プロセス案を示す。物質設定や実行方式を黙って変更しない。

ローカル入力検証後に群間の計画一致を確認し、全ランクで同じ順序のコールバックへ入る。native停止や一方のランクの消失から安全に復帰できるとは保証しない。停止・タイムアウト・診断回収の限界をアダプターごとに示す。

## 10. 初期状態、記録、再開

IDとは別に内容のダイジェストを持つ。material_idが同じでもパラメータ・外部データが変わったら検出する。次を分けて保存する。

- 科学入力: 単位正規化・既定値展開済みの設定、初期状態、物質配置、データ参照とハッシュ。
- 実装: backend/契約/パラメータスキーマの版、ライブラリやコード・依存関係の識別。
- 実行: MPI分割・スレッド・プラットフォーム・資源計測の方法と成否。

canonical JSONは版付き規則を定義し、重複キーとNaN/Infを拒否する。外部ファイルはストリーミングhash等で扱い、巨大な配列をJSON本文へ埋め込まない。型、配列shape/dtype、単位を保持する。ハッシュ一致は内容識別であって、物理的妥当性や全機種でのビット一致の保証ではない。

出力はrun/material/point/initial-state参照、配列の点順対応、単位・時刻配置を伴う。IDと実行条件の対応はmanifestで一度保存でき、毎stepで文字列を送信・重複保存する必要はない。

再開にはbackendと形式の互換性、内容の整合、point_id対応を検査する。再開実行には新run_idとparent_run/checkpoint参照を与え、元の物質・点IDを引き継ぐ。並列割当変更はcheckpoint/backendが明示的に対応する場合だけ許す。分岐は元の状態を書き換えない。

## 11. 入力例（書式案、未実装）

以下は組み込みLDと利用者のSBEモデルを同じ配置へ登録する例。数値・スキーマは説明用であり、検証済み物性・そのまま実行可能な入力ではない。実際のfield設定は選択した場バックエンドのスキーマで検証する。

```json
{
  "schema": "salmonpy.simulation/1",
  "materials": {
    "metal": {
      "model": "ld",
      "backend": "builtin_ld",
      "parameters": {"source": "materials/metal.json"}
    },
    "silicon": {
      "model": "sbe",
      "backend": "my_sbe",
      "parameters": {
        "bands_file": "data/si_bands.npz",
        "dephasing_time": {"value": 10, "unit": "fs"}
      }
    }
  },
  "initial_states": {
    "si_equilibrium": {
      "material_id": "silicon",
      "prepare": {"occupation": "equilibrium"}
    }
  },
  "placement": {
    "layers": [
      {"layer_id": "front", "material_id": "metal", "thickness": {"value": 10, "unit": "nm"}},
      {"layer_id": "back", "material_id": "silicon", "initial_state_id": "si_equilibrium", "thickness": {"value": 20, "unit": "nm"}}
    ]
  },
  "field": {
    "backend": "registered_field",
    "parameters": {
      "dimension": 1,
      "spacing": {"value": 5, "unit": "nm"},
      "source": "fields/pulse.json",
      "boundary": "fields/boundary.json"
    }
  },
  "execution": {
    "budget": {"mpi_ranks": 4, "threads_per_rank": 1, "memory": {"value": 4, "unit": "GiB", "scope": "job"}},
    "field": {"ranks": 2},
    "assignments": [
      {"select_layer": "front", "mode": "field_local"},
      {"select_layer": "back", "mode": "dedicated", "ranks_per_group": 1, "placement": "auto"}
    ]
  }
}
```

`placement:auto`は点数と能力を見て具体的なgroup_id・rank・point_id対応を提案する要求であり、無制限なプロセス生成許可ではない。残る2ランクで配置できない点数/モデルなら計画を拒否し、必要資源を表示する。field_local側のメモリもjob予算へ含める。

物質ごとのDFT/TDDFT設定では、そのbackendのparameters内に構造・XC・擬ポテンシャル・電子grid・kpoints・bandsを定義する。共通の数値定義を再利用しても、物質間で値の共通化を強制しない。

Python側の概念例:

```python
registry.register_material("my_sbe", MySBEAdapter())
config = load_config("simulation.json", registry=registry)
plan = resolve_plan(config, registry=registry)
print(plan.summary())
```

これらは提案API。自作コードの登録は利用者が明示的に行う。通常利用で毎回対話承認は要求しないが、実行計画と採用値は確認・保存できるようにする。

## 12. 初心者と熟練者の入口

初心者には目的、メモリ上限、並列数を聞き、既存の入力・物質設定から分かる値は聞き直さない。用途別の最小サンプルと採用条件の短い一覧を示す。熟練者には物質別・群別の詳細指定を許す。

メモリ見積もりがない自作モデルはunknownと表示する。宣言値・推定値・実測値を区別し、保証できない上限を保証と表示しない。厳格な予算要求には実測/実行環境の制限手段を含めた別の検証が必要。資源計測の失敗と計算の失敗を分けて報告する。

エラーは設定パス（例: materials.silicon.parameters.kpoints.mesh）、期待条件、受け取った値、修正例を含む。未対応条件は停止し、収束未確認などの科学的限界は結果と一緒に明示する。

## 13. 既存実装との対応と移行

| 既存部品 | 本設計での扱い |
|---|---|
| materials.bind_material / check_material | 直列自作Aモデルの接続・限定適合試験として再利用 |
| material_response.MaterialBinding / ResponseSession | IDと解決済み定義をbindingへ載せる。prepare/create_state/advance経路はアダプターで接続 |
| distributed.ParallelPlan / ParallelContext | 解決済み配置とassignmentから生成。既存ホストcommを使用 |
| c_material.CMaterial、材料C ABI | 既存の版付き直列ABIを維持。MPI ABIや新規ABIへ勝手に置換しない |
| maxwellの場とcouple、既存E/H結合 | 既存の時刻契約を維持。custom fieldのMPI利用は能力確認後に実装 |
| 初期状態/出力アーカイブ | material/point/run参照を版付きメタデータとして追加。旧形式は明示変換 |
| 内部GS/TDDFT設定構造体 | 検証した選択値を直接渡す。global値の切替で独立性を装わない |

既存C ABIの原子的失敗契約は弱めない。Python側の自作モデルやnative solverで同じ保証がない場合はその差を明示する。`check_material`は呼び出し側が指定した代表波形での検査であり、全入力の科学的妥当性・MPI・失敗原子性まで証明するものではない。

## 14. 受け入れ条件と実装順

既存の共有入力分離に合わせ、次の順で追加する。

1. 共通定義、JSON/Python共通検証、ID参照、物質ごとの設定と解決結果保存。
2. 既存LD/SBE・自作Pythonモデル・既存材料C ABIへの薄い登録アダプター。
3. 配置展開と実行群計画、MPI能力照合、既存応答サービスへの接続。
4. 初期状態/出力/checkpointへのID・内容・版の継承。
5. バックエンド能力に応じた再開・追加観測量などの拡張。

最低限の受け入れ試験:

- JSONとPythonが同じ解決済み設定を作る。未知/重複キー、不正単位、参照切れ、非有限値を拒否。
- 同じmaterialを複数点へ置いて異なるA履歴を与え、独立実行と比較。異なるmaterialの固有設定も混ざらない。
- 非連番/文字列ID、辞書順変更、MPI割当変更でも物質・点・出力の対応を保持。
- 同物性・異IDでも界面計算が変わらない。
- 組み込みと自作Python/C実装を入れ替え、単位/符号/時刻契約を照合。
- serialモデルの複数ランク群への誤割当、予算不足、異なるランクの計画不一致、未対応能力を実行前に拒否。
- 一部step失敗時にセッションが誤って継続しない。原子的復元は対応実装だけで検証。
- 再開後のID継承、版/内容不一致の拒否、未対応の再分割の拒否。
- 検索や設定ロードだけでコンパイル、MPI初期化、ネットワーク通信、ワーカー起動を行わない。
- 日英ガイドとAI検索JSONの生成・同期を検査。最小例をwheel導入環境から実行。

今回の改訂は設計文書のみ。上記の共通設定API、registry、simulation JSON形式、能力照合・IDの全工程継承を実装済みとして公開マニュアルへ登録しない。

## 14. 実装分割と構造入力（2026-11-15追記）

最初に設定だけの`salmonpy.materials/1`を実装し、全計算のsimulation形式は受け付けない。
registryの検証関数、物質定義、初期状態ID参照の検査から始める。既存native分離とは別の進捗として扱う。

ASE AtomsをPython入口にし、スーパーセルなどは物質ごとに別の構造ファイルを参照する。
参照にはpath・format・必要時frame・出典を持たせ、読込時の内容hashと採用構造を保存する。
入力JSONに大量の原子座標を転記させず、元ファイルのセル/原子数/配置を黙って標準化・変換しない。
単位・周期性・電荷/磁性・backendが扱える幾何を検査する。単位不明の形式は推測しない。
パスの基準は入力ファイル所在。Python Atomsからは同等の構造記録を作り、ファイル保存を必須にしない。
MateriAppsは検索入口であり、単一の構造APIではない。提供元のID・版・URL・利用条件を記録し、
CIF等を明示取得してASE読込へ渡す。構造取得とXC/PP選択は分離する。

直交周期セルの希望最大幅h_iからN_i=ceil(L_i/h_i)を出発点とし、backendが要求する
最小点数/倍数を満たす最小の点数へ切り上げる。実際のh_i=L_i/N_i、希望値、丸め理由、
総格子数を報告・保存する。現行DFTは各軸8以上だが、全backend共通条件にしない。
格子幅と点数の同時指定は拒否。固定済み科学設定をMPI割当に合わせて黙って再丸めしない。
非直交セルには長さだけの式を流用せず、メトリックとbackendの対応範囲を別途検証する。
孤立系の端点/真空/halo、FDTD格子も別の契約で扱う。格子数の自動化は収束保証ではない。
