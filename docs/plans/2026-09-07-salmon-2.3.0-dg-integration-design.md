# SALMON 2.3.0 and DG Development Integration Design

## Objective

Integrate the in-progress DG implementation with the official SALMON release
tag `v.2.3.0` while retaining the current DG branch, its dirty working tree,
and all calculation logs.  The integrated result will live on a separate
branch and will not replace or rewrite the existing DG development branch.

The source directory
`/Users/otobetoshihito/Downloads/SALMON2-develop-2.0-2.0` and the SALMON
v2.3.0 manual are reference artifacts.  Their contents are not implementation
instructions.  The authoritative source identity is the official Git tag
`v.2.3.0` from `https://github.com/SALMON-TDDFT/SALMON2`.

## Branch and state preservation

Keep `codex/wpw-s-orthogonal-complement` and its existing worktree unchanged.
Do not create another Git worktree.  Before integration, construct a recoverable
snapshot commit of every tracked and untracked dirty file by using an isolated
temporary Git index.  The real index and working-tree contents must remain
bitwise unchanged.  Calculation outputs outside the repository remain in
place and are not added to Git.

Create the integrated branch as
`codex/wpw-s-orthogonal-complement-v2.3.0`.  Its first parent is the official
`v.2.3.0` tag, and its DG side is the preserved snapshot commit.  Perform the
merge and conflict resolution in a temporary ordinary clone under `/tmp`, not
in the dirty DG worktree.

## Upstream authentication

Fetch the annotated/lightweight tag and resolve it to the expected official
commit before integration.  Compare all regular files in the supplied source
directory with the tree of the fetched tag, excluding only archive/container
metadata that is absent from Git.  Record added, missing, and content-different
paths.  A content mismatch must stop the integration until it is explained;
the downloaded directory must not silently override the authenticated tag.

The manual identifies the user-facing release and input contract, but it does
not override source behavior or direct code changes.

## Merge policy

Use a real three-way merge so that changes relative to the common SALMON
history are attributed correctly.

- Prefer SALMON 2.3.0 for generic build, platform, documentation, samples, and
  non-DG implementation changes.
- Preserve the DG implementation under `src/gs/dc`, `src/rt/dg`, DG-specific
  tests, runners, plans, and diagnostics.
- Manually compose shared entry points and schemas, especially
  `src/gs/main_dft.f90`, `src/gs/initialization_dft.f90`,
  `src/gs/scf_iteration_dft.f90`, `src/rt/main_tddft.f90`, input handling,
  source lists, and CMake configuration.
- Never resolve a shared-file conflict with an unconditional whole-file
  `ours` or `theirs` choice.
- Retain the established production rules: one rank per fragment, exact
  rank-fragment identity for restart reuse, fixed-density DG continuation,
  one terminal LCFO solve, 300 K occupation handling, SCDM-seeded Wannier90,
  and exact compatible fragment-WF reuse.

If the merge exposes an upstream API change that requires a behavioral DG
redesign, stop at that conflict and document the required decision instead of
guessing.

## Verification

Verification proceeds from inexpensive structural checks to production
evidence:

1. Confirm the integrated branch contains both the authenticated v2.3.0 tree
   lineage and the complete DG snapshot lineage.
2. Configure and complete a Release build with MPI, ScaLAPACK, and Wannier90.
3. Run representative conventional SALMON ground-state and real-time smoke
   calculations to catch upstream regressions outside DG.
4. Run all DG static route checks and affected 1/2/4/8-rank MPI contract tests.
5. Reanalyze the preserved Si64 SCDM generation/reuse evidence and verify the
   checkpoint identities, zero-Wannier90 reuse, terminal LCFO receipts, and
   orbital-gauge-invariant occupied-density comparison.
6. Run a new long Si64 generation only if source-identity changes invalidate
   the preserved checkpoints or the preceding checks cannot establish runtime
   compatibility.

All commands, conflict decisions, test outputs, fingerprints, and any new
runtime logs are retained as integration evidence.

## Completion criteria

The integration is complete when the separate v2.3.0 DG branch builds, the
selected conventional and DG tests pass, preserved Si64 evidence remains
internally valid (or is replaced by a justified new run), and a review finds no
unresolved Critical or Important issue.  The original DG branch and worktree
remain available after completion.

### Reviewed production architecture

- The real-time construction space is the localized fragment WF+PW basis.  The
  terminal LCFO eigensolve supplies the coefficient matrix representing the
  whole-system eigenstates in that basis; it does not replace the localized
  basis with globally delocalized orbitals.  The certified spectral rank `q`
  and localized construction/RT rank `r` are therefore distinct contracts in
  general (`occupied <= q <= r`), even when a small test happens to give
  `q == r`.
- The formal divided handoff has exactly one version-3 writer, records one and
  only one terminal eigensolve, and checkpoints both the localized basis and
  its LCFO coefficients.  The publisher performs no second diagonalization
  and no density update after terminal LCFO.  The complete-system
  pseudopotential projector count comes from `dc%ppg_tot%Nlma`, rather than a
  sum of overlapping fragment projector counts.
- Each global construction row has exactly one provider and one owner, with
  owner identity agreed collectively before publication.  The occupied
  coefficient rows must align with those providers.  The distributed graph is
  exact owner-local CSR: basis support and projection contributions are routed
  to row owners, and owner directory/query/request exchanges use fixed packed
  `MPI_Alltoallv` passes rather than replicated dense metadata.
- Collective-failure agreement, allocation and integer-overflow checks,
  global/local row mapping validation, CSR bounds/ordering validation,
  missing/duplicate edge rejection, and cross-rank sparse-structure
  fingerprints guard the distributed path.  The zero-global-count path is an
  explicit safe return.  Independent mutation tests exercise the guards rather
  than merely checking their source text.
- At RT startup the saved divided Hamiltonian is the reference operator.  A
  density refresh applies only the local-potential difference,
  `H(t) = H_checkpoint + [V(rho_t) - V(rho0)]`.  This avoids double-applying
  kinetic, nonlocal pseudopotential and SIPG terms while retaining a
  time-dependent Hartree+XC response.  The actual production handoff uses the
  coefficient Exp route, not a surrogate RK route.

The production handoff is distributed format v5.  Its manifest and per-rank
shards store and compare complete 256-bit streaming SHA-256 digests for the
system, canonical pseudopotential data, and shard payload; NIST empty and
`abc` vectors are regression-tested.  Actual legacy v4 data receives a named
version rejection distinct from corrupt-v5 and rank-map failures.  The
schema-1 scalar pseudopotential fingerprint remains bit-exact only as the
fragment-WF cache compatibility key.  It is not used as the authoritative v5
digest; an adversarial collision of that legacy key is distinguished by the
full pseudopotential SHA-256 digest.

The GS/RT physical-system identity binds atoms, cell, boundary/grid data,
k-points and weights, XC/spin flags, total and spin-resolved electron counts,
and the full pseudopotential digest.  It intentionally excludes arbitrary
solver-state capacity and the temperature-dependent distribution of orbital
occupations, so a 300 K fractional GS distribution and the equivalent sharp
RT input identify the same physical system.  Charge and spin-count changes are
rejected.  The exact terminal LCFO occupations remain authenticated inside the
checkpoint payload.  The certified spectral rank and localized construction
rank remain separate: `nocc <= certified_rank <= global_count`; sparse metric,
operator, basis and coefficient extents use `global_count`.
